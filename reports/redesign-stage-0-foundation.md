## The font-pipeline correction (as flagged in the brief)

The brief's builder prompt assumed the interactive dashboard consumes `report-fonts.js`'s
self-hosted `FONT_FACE_CSS`. It does not — only `report-pdf-renderer.js` does. The interactive
dashboard and the HTML report preview (`report-renderer.js`) both load fonts from a Google Fonts
CDN `<link>` (Space Grotesk + IBM Plex Sans). Per the corrected instructions, I did **both**:

1. **Self-hosted IBM Plex Mono through the real pipeline.** Tooling was available
   (`python3 -m fonttools`/`brotli` present; `github.com` reachable), so I extended
   `build-report-fonts.sh` and regenerated `report-fonts.js`. One wrinkle: IBM Plex Mono ships
   as **static per-weight TTFs** in the `google/fonts` OFL repo (no variable `wght` axis, unlike
   Inter/Source Serif 4), so the instancer step is skipped for it — the build script now has a
   `buildStatic()` helper alongside the existing `build()` (instancer + subset) for the two
   variable fonts. Weights 400/500/600 embedded as `'TIS Mono'`.
2. **Added IBM Plex Mono to the CDN `<link>`** in both `build-interactive.js` and
   `report-renderer.js`, so `--f-mono` actually renders in the browser this stage (the dashboard
   doesn't read `report-fonts.js` at all).

`--f-mono: 'IBM Plex Mono', 'SFMono-Regular', Menlo, Consolas, monospace;` is introduced in the
new additive token layer (not by touching `reportCss`'s `--f-display`/`--f-body`, which are
untouched this stage).

## Design tokens introduced (`scripts/build-interactive.js`, `css()` function)

Two additive layers already existed (`reportCss`'s base `:root`, then the existing "Batch F"
`:root`). I added a **third**, under its own namespace (`--fs-*` for the type scale, `--g-*` for
color/motion roles) rather than redeclaring the Batch F `--type-*`/`--role-*` names — this stage
re-skins only the app shell + waterfall; other sections keep reading Batch F tokens unchanged
until their own staged diff repoints them.

- **Type scale (px):** `--fs-label:10 --fs-caption:12 --fs-body:13 --fs-input:13 --fs-data:13
  --fs-value:15 --fs-heading:16 --fs-kpi:24 --fs-display:32`. `--f-mono` + `tabular-nums
  lining-nums` are applied at the call sites for data/value/kpi/display (mono is a font choice,
  not baked into the size token).
- **Color roles** (aliases onto existing hex — no new palette): `--g-canvas` (`var(--bg)`,
  #f6f7f8), `--g-panel` (`var(--white)`), `--g-chrome-ink` (#242331, same as `--ink`),
  `--g-chrome-ink-inverse` (#f0f1f2 — new, inverse text), `--g-text-slate` (`var(--slate)`),
  `--g-hairline` (`var(--border)`, rgba(113,124,137,.18)), `--g-brand-red` (`var(--red)`,
  #d41d1d — wayfinding/identity only, never P&L), `--g-positive`/`--g-loss`/`--g-caution` (alias
  the existing Batch C/F role values), `--g-shadow-elevation` (one neutral shadow, reserved for
  overlay/drawer — not used anywhere yet this stage).
- **Spacing:** reused the existing `--space-1..8` scale, not redefined.
- **Motion:** `--g-duration-fast:120ms --g-duration-ui:160ms --g-duration-surface:220ms`,
  `--g-easing-standard:cubic-bezier(.2,0,0,1)`, `--g-easing-exit:cubic-bezier(.4,0,1,1)`. Applied
  to `.kpi-flash` (opacity-only, unchanged visual, now named tokens) and `.results-sticky-kpi`'s
  existing transition. A `@media (prefers-reduced-motion: reduce)` block collapses transition/
  animation duration to `.01ms` for the new component classes.

## A bug found and fixed during this stage

My first draft of the new `:root` token block's leading comment used the shorthand
`--type-*/--role-*` to mean "the Batch F `--type-*` and `--role-*` names". That literal substring
contains `*/`, which the CSS tokenizer reads as a comment-close — it silently truncated the
comment early and corrupted parsing of everything after it, so the entire new `:root` block (and
by extension every `--fs-*`/`--g-*`/`--f-mono` token) failed to register in the stylesheet at all.
Symptom: the header rendered with a transparent background and near-invisible text (confirmed via
`getComputedStyle` — `--g-chrome-ink` resolved to `''`, `.report-header` background computed to
`rgba(0,0,0,0)`). Found by diffing before/after screenshots, then confirmed via a byte-level
`/*`/`*/` balance check across the generated `<style>` block (a general technique worth keeping:
count comment-open/close pairs sequentially and flag unmatched ones — the file already carried one
pre-existing, harmless stray `*/` elsewhere, unrelated to this bug, which I left alone as
out-of-scope). Fixed by rewording the comment to `--type- / --role-` (no adjacent `*/`). Rebuilt,
re-screenshotted, confirmed correct rendering, and re-ran the full engine guard (unaffected either
way, since this was pure CSS).
